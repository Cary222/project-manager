## 一、这些问题体现了哪些重要的工程原则

### 原则 1：环境差异即 bug（跨平台意识）

**涉及的代码：** `lib/git-sync/repos.ts:4`

```typescript
export const ROOTS = ["/home/hxy/work/company", "/home/hxy/work/personal"];
```

**为什么重要：**

你已经在路线二（排错基本功）里学过 Git 原理，知道 Git 的本质是文件系统。但这个 bug 揭示了一个更底层的原则：**代码里出现的每一个字符串，都可能成为跨环境的定时炸弹。**

`/home/` 是 Linux 标准路径前缀。macOS 的用户目录在 `/Users/`。当代码在 macOS 开发、在 Linux 生产运行时，这个路径在两个环境里都不存在——只是表现不同：

| 环境 | 结果 |
|------|------|
| macOS 开发机 | `fs.readdir("/home/...")` → 直接报错 "No such file or directory"，git-sync 完全失效 |
| Linux 生产机 | `/home/hxy/` 存在，逻辑正常 |

类比：就像用中文写请假条交到外企——代码在本地"能跑"，到线上就挂。你已经从排错基本功里知道这个模式：**环境差异是最隐蔽的 bug，因为它在开发环境不暴露。**

**延伸思考：**

- 变量抽离到 `.env` 还是硬编码——不只是一个"风格问题"，是"能不能跨环境用"的问题
- 这次用 Linux 路径，下次可能是 Windows 的 `C:\`。Node.js 的 `os.homedir()` / `os.platform()` 是跨平台的标准解法
- 测试时在 CI 镜像里跑一遍能发现这类问题（不同 OS = 不同 CI runner image）

### 原则 2：幂等性是增量的前提（状态管理完整性）

**涉及的代码：** `lib/git-sync/scan.ts:40-78`

增量同步的核心逻辑：

```typescript
// 有游标 → 增量
if (cursor?.lastCommitAt) {
  const since = new Date(cursor.lastCommitAt.getTime() - 3600_000);
  args.push(`--since=${since.toISOString()}`);
}
// 无游标 → 仅取最近 SCAN_LIMIT 条
```

**为什么重要：**

增量更新的本质是"记住上次做到哪"。游标（Cursor）是这次修复引入的状态持久化机制——把 `lastCommitAt` 存在 PostgreSQL 的 `syncCursor` 表里，下次只拉那之后的 commit。

问题在于：**首次运行时，游标不存在，代码退化为"只取最近 500 条"。**

这会导致什么后果？

```
第1次同步（无游标）→ 取最近500条 → ✅ 正常
第2次同步（有游标）→ `--since` 只取增量  → ✅ 正常
```

但如果项目历史超过 500 条 commit：

```
第1次同步 → 500条之后的历史全丢了
第2次同步 → 游标指向第500条 → 只取增量 → 第501条及以后依然在
```

**核心问题**：首次同步不完整，游标指向了错误的历史位置，之后永远追不回丢失的 commit。

类比：就像搬家时让搬家公司"只搬最近搬过的 500 箱"——如果仓库有 1000 箱，后 500 箱从此消失了。

**延伸思考：**

- 幂等性 = "运行 1 次 = 运行 100 次，结果一样"
- 增量的每一步都要问：如果这是第 1 次运行，会怎样？
- 游标表本身也是一种"状态"，状态初始化不完整 = 后续所有逻辑都建立在错误基础上

### 原则 3：工具的参数有语义顺序（CLI 契约与行为契约）

**涉及的代码：** `lib/git-sync/scan.ts:46-51`

```typescript
const args = [
  "log",
  "--all",
  `--max-count=${SCAN_LIMIT}`,
  "--format=%H|%aI|%an|%s",
];
```

**为什么重要：**

Git log 的参数顺序在大多数情况下不影响结果——但 `--since`（以及其他 revision specifier）有一个关键语义：**它们定义"从哪里开始"的边界条件。**

`--all` 的语义是"遍历所有分支"。当它和 `--since` 组合时：

```
git log --all --since="2026-07-01"
```

这个命令的行为是：**在所有分支上，找 commit date >= 2026-07-01 的 commit**。Git 的 commit date（author date / committer date）是 commit 本身的元数据，不受分支限制。

但这里有个边界 case：如果一个 commit 在 7 月 1 日被 merge 到 `main`，但它本身的 commit date 是 6 月 15 日，`--since=7-01` 会**包含**它（因为 merge commit 本身的 date 是 7 月 1 日）。这是对的。

真正的问题可能出在：**当游标丢失或被重置时，`--since` 窗口的设计是否能兜住所有边界情况？**

类比：`git log` 的参数就像调收音机频道——转对位置就能收到台，但旋钮的刻度不一定和你想的一样。理解每个参数"过滤的是什么"比记住顺序更重要。

**延伸思考：**

- 每次调用外部 CLI 前，读一遍官方文档的"DESCRIPTION"章节（不只是 examples）
- 参数契约 = API 契约，破坏契约的行为在不同版本可能不同
- 用 `--help` 或 `man git-log` 验证关键参数的行为，比搜索引擎更可靠

### 原则 4：自动化是可靠性的一部分（人肉流程即债务）

**涉及的代码：** 缺失的部分（没有定时任务入口）

**为什么重要：**

Git sync 目前依赖手动触发。在你路线三（项目进阶功能）的记录里，已经实现了：
- 异步 Job 系统（Worker + Background Jobs，2026-06-26）
- 全局事件追踪系统（2026-06-24~26）

Git sync 没有接入这个系统，意味着：

| 场景 | 有定时任务 | 无定时任务 |
|------|----------|----------|
| 用户 push 后 | 自动同步，工单秒级关联 commit | 依赖用户手动点同步 |
| commit 漏关联 | 自动补齐 | 需要人工发现再补 |
| 服务器重启 | 任务继续 | 需要重新手动触发 |

类比：就像买了高级烤箱但每次做饭都要守在旁边——工具再强，不自动化就不省力。

**延伸思考：**

- "人肉流程"是技术债，因为它消耗注意力，而注意力是有限的
- 在路线三里你已经做过 Background Jobs 系统，Git sync 是天然的受益者
- 每次加新功能时，问一句"这个要定时跑吗？"——早接比晚接成本低

## 二、类似问题在生产环境会导致什么后果

### 后果 1：静默数据丢失（最危险）

跨平台路径问题在 macOS 开发时就会暴露（报错），但在 Linux 生产机上反而"正常"。真正危险的是**反过来**：在 Linux 上开发没问题，部署到 Windows/容器就挂。

Git sync 的数据丢失场景：

```
首次同步时，游标初始化不完整
→ 500条之后的 commit 永久丢失关联
→ 用户以为"所有 commit 都能关联工单"
→ PM 查工单 "#10044" 时发现 commit 列表不全
→ 无法追溯真实编码量和技术决策
```

**这类后果的特点**：不报错，但数据不对。排查难度极高，因为"没有报错"会误导排查方向。

### 后果 2：跨团队协作失效

Git sync 的核心价值是**commit 自动关联工单**。一旦失效：

```
程序单 #10100
  ├── commit a1b2c3d "feat: 修复登录 bug"  ← ✅ 关联
  ├── commit d4e5f6g "fix: 处理 token 过期"  ← ❌ 丢失（500条之后）
  └── commit h7i8j9k "refactor: 简化权限校验"  ← ❌ 丢失（500条之后）
```

代码在，但 commit 历史和工单的对应关系断了。PM 无法从工单追溯代码变更，Code Review 的上下文丢失。

### 后果 3：定时任务缺失导致运维负担

每次服务器重启、CI/CD pipeline 重建，都要手动触发同步。这在初期可以接受，但随着项目增多：

- 10 个仓库 → 10 次手动操作
- 忘了触发 → commit 和工单长期不同步
- 换人接手 → 不知道要手动同步这回事

## 三、Code Review 中重点关注的模式

### 模式 1：硬编码的路径 / 环境特定字符串

**Checklist：**
- [ ] 路径是否用了 `path.join()`（跨平台）
- [ ] 是否用了 `os.homedir()` / `process.env` 动态获取
- [ ] 是否有对应的 `.env.example` 记录

**ProjectHub 里的例子：**
- `lib/git-sync/repos.ts:4` — `ROOTS` 硬编码 → 应改为 `process.env.GIT_SYNC_ROOTS` 或读取配置文件

### 模式 2：状态初始化完整性（首次运行的边界）

**Checklist：**
- [ ] 有"增量"逻辑时，问：第 1 次运行（无状态）会怎样？
- [ ] 游标 / 缓存 / 锁文件在"第 1 次"时的默认值是什么？
- [ ] 边界条件是否有日志输出？（`console.log("DEBUG cursor:", ...)` 是好的实践）

**ProjectHub 里的例子：**
- `lib/git-sync/scan.ts:44` — `prisma.syncCursor.findUnique` 返回 `null` 时的处理逻辑是存在的（`if (cursor?.lastCommitAt)`），但首次运行的 fallback 逻辑（仅取 500 条）是否有明确注释和警告？

### 模式 3：CLI 参数的行为契约

**Checklist：**
- [ ] 调用外部 CLI（git, ffmpeg, python 等）前，查过官方文档的"OPTIONS"章节
- [ ] 关键参数（边界条件、过滤条件）有单元测试或集成测试覆盖
- [ ] 不同版本的行为差异有记录（`# major.minor.patch` 版本锁定）

### 模式 4：自动化 vs 手动触发的边界

**Checklist：**
- [ ] 新增的功能是否有对应的"定时触发"需求？
- [ ] 如果有，是否已接入 Background Jobs / Cron 系统？
- [ ] 手动触发时，是否有"当前状态是什么"的诊断信息？

## 四、可沉淀的检查清单

### 清单 A：跨平台代码检查（每次 Review 必须过）

```
□ 所有路径用 path.join() 或 path.resolve()
□ 不使用 /home/, C:\, /Users/ 等 OS 特异路径
□ 环境变量读取使用 process.env.X，默认值写在 .env.example
□ 在 CI 多 OS 环境（Ubuntu + macOS + Windows）跑测试
```

### 清单 B：增量 / 状态同步代码检查（每次 Review 必须过）

```
□ 第 1 次运行（无状态）时的行为已明确定义
□ 状态初始化失败时有明确错误或 fallback
□ 游标 / 偏移量 / 时间戳等边界值有日志
□ 首次全量 vs 增量逻辑的覆盖范围已注释说明
```

### 清单 C：CLI 调用检查（每次 Review 必须过）

```
□ 调用的 CLI 参数顺序和组合查过官方文档
□ 关键参数（过滤、范围、格式）有单元测试
□ 超时和错误处理已实现（execFileAsync timeout）
□ 输出解析有容错（空输出、异常格式）
```

### 清单 D：自动化就绪检查（新功能上线前必须过）

```
□ 功能是否需要定时触发？ → 接入 Background Jobs
□ 功能是否有手动诊断入口？ → 写入 /api/admin 或管理后台
□ 任务失败是否有告警？ → 接入 PM 的事件追踪系统
```

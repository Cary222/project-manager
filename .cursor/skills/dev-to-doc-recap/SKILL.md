# Dev-to-Doc Recap（功能完成 → 可复现 MD）

> 目标：把刚刚做完的功能（**开发 + 测试**）写成一篇 MD，**让一个不懂背景的新手**第一次读到就能看懂，**且未来拿到这份 MD + 仓库 commit** 就能完整复现。

---

## 何时触发

用户发出以下任一类指令时使用本 skill：

- "帮我把这个功能从开发到测试全部写成一个 md"
- "写一份知识笔记 / 复现文档 / 操作手册"
- "总结一下这次实现"
- "下次有人接手，能照着这份文档做出来"
- "我要交接 / 留档"

> 核心判断：用户 **已经完成开发 + 测试**，希望把"过程 + 步骤"沉淀成 MD。**不是**写新功能。

---

## 工作流（7 步，按顺序执行）

### Step 1：定位"这次做了啥"

先盘点仓库里 **未提交 / 未推送** 的改动，识别"范围"：

```bash
git status -s
git diff --stat
git log --oneline -5           # 看一下 commit 风格
```

同时问自己 / 找信息源：

- 用户是改了几个文件，还是新增了一个模块？
- 改了哪些层？（前端 / 后端 / 数据库 / 部署脚本 / 依赖）
- 跑过哪些验证？（curl 探活、reindex、单元测、浏览器手测）

### Step 2：读源 + 读上下文（**只读，不改代码**）

至少把以下三类信息吃透，再下笔：

1. **改过的核心文件全文**（不只 diff，要看完整上下文）
2. **调用链上下游**：谁调我？谁被我调？环境变量从哪读？
3. **部署 / 启动方式**：服务跑在哪个端口、用什么命令、配置文件在哪

> ⚠️ 不要凭空想象"应该怎么工作" — 文档必须能 1:1 复现，必须**只写代码里实际存在的**行为。

### Step 3：开新 MD 之前问用户 2 个问题

用 `AskQuestion` 工具收集（**不要替用户决定**）：

1. **文档放哪？** 默认建议 `docs/<功能名>.md`，但允许用户指定（如 `docs/embedding/PDF_EXTRACT.md`）。
2. **读者是谁？** 选项：
   - 未来自己（默认）— 简洁 + 链接到代码
   - 团队新人 — 详细解释概念、命令全列
   - 以上两者
   - 完全外行 — 配图 + 流程图

> 这两个问题不解决，写出来的文档**注定**有人看不懂。

### Step 4：写文档 — 8 段式骨架

任何"开发测试复现 MD"都按下面这 8 段写。**不要漏段**。

| # | 段落 | 必须包含 |
|---|------|----------|
| 1 | **目标 & 背景** | 这功能解决什么问题？旧版为什么不够？（新人第一眼最需要） |
| 2 | **改动清单** | 改了 / 新增哪些文件，每个文件的"作用一句话" |
| 3 | **核心实现** | 关键代码块 + 注释"为什么这样写"。**贴真实代码**，不是伪代码 |
| 4 | **环境与配置** | 端口、env 变量、依赖版本、模型路径 |
| 5 | **启动 / 部署命令** | 完整可复制的 bash，**路径要写绝对路径**（新人不可能猜） |
| 6 | **测试 & 验证** | 验活的 curl / 脚本命令 + **期望输出**（这是判断"我跑对没"的关键） |
| 7 | **复现 Checklist** | 10-15 行 markdown checklist，新人照着打勾就能完事 |
| 8 | **踩坑记录** | 这次开发**实际遇到**的问题、报错信息、根因、解法。按时间顺序。每条 3-5 行。**这是让新人避开同类陷阱的关键章节**，不能省 |

> 段 2、段 5、段 6、段 8 是**最不能省**的。没有段 2 不知道改了什么，没有段 5 跑不起来，没有段 6 不知道对没对，没有段 8 新人会踩同样的坑。

> **段 8 怎么写**：从 `git diff`、终端日志、agent transcript 里反推这次实际遇到过哪些错误。每个坑写「现象 / 原因 / 解法」三段式即可。如果本次开发一路顺畅没有任何报错，可省略本段，但**绝大多数功能都有坑**，写出来比不写强 10 倍。

### Step 5：引用代码用代码引用块，不是 markdown 代码块

文档里要"展示某段代码"时，**优先用**：

```startLine:endLine:path/to/file.ts
// 真实代码
```

**而不是**把代码重新抄一遍到 markdown 里。原因：

- 真实代码会随仓库 commit 更新，文档里的"代码块"会立刻过期
- 行号方便定位

> 例外：少于 3 行的纯配置 / 命令，可以直接用 ```bash 块。

### Step 6：写完做 3 项自检

文档落盘后，回头看：

- [ ] **新人自检**：把自己当成"第一次看到这个项目"的人，有没有不懂的概念没解释？
- [ ] **命令可执行性**：所有 bash 命令独立复制粘贴能不能跑通？路径是绝对的还是相对的？
- [ ] **预期输出有贴**：每个验证命令后面都写了"期望看到什么"吗？没有的话，跑了也不知道对没对。

### Step 7：把文档**真实落到磁盘** + 链接进相关文档

- 写入用户指定的路径
- 如果仓库有 `docs/README.md` 或 `docs/OPERATIONS.md`，在合适位置加一行链接
- 提示用户："文档已写到 X，是否要 commit？"

## 常见坑（避雷）

> 以下是"**写文档本身**"容易踩的坑，不是功能开发过程中的技术坑（那些应该写在文档的段 8「踩坑记录」里）。

1. **写了代码块但没引用真实文件** → 仓库一更新文档就过期。永远用 `startLine:endLine:path` 引用。
2. **没贴"期望输出"** → 新人跑了不知道对没对。每个验证命令后面必须贴期望。
3. **路径写 `~` 或相对路径** → 复制粘贴的人可能 `pwd` 不一样。绝对路径最稳。
4. **忘了写"复现 Checklist"** → 新人看完文档不知道从哪一步开始动手。Checklist 是入口。
5. **没解释"为什么"** → 只贴代码不解释设计意图，新人看完还是不知道为啥这么写。
6. **没问读者是谁** → 写给"自己"和写给"新人"完全是两种文档，结构都要变。
7. **没写踩坑记录** → 这次开发路上遇到的所有报错、绕路、失败方案都丢了，新人接手时会踩同样的坑。**必须**把开发过程的踩坑沉淀到文档段 8。

## 与其他 skill 的协作

- 本 skill 只生成 MD 文档，**不**自动 commit。如果用户要 commit，引导他们用 `git-commit-assistant` skill。
- 本 skill 与具体技术栈无关。可用于 pm 项目，也可用于其他项目。
- 如果用户既要写文档又要写代码，**先写代码 + 验证**，完成后再调用本 skill。
